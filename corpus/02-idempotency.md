# Idempotency

Every write endpoint on the Northwind Payments API accepts an idempotency key.
This document explains how keys behave, how long they live, and the cases where
people most often get them wrong.

## Sending a key

Pass the key in the `Idempotency-Key` header:

```
POST /v1/payments
Idempotency-Key: 8f14e45f-ea0c-4b3d-9f2a-2c1f6d3e5a77
```

Keys must be between 16 and 255 characters. We recommend a UUID v4 per logical
operation. The key must be generated by the merchant, not derived from the
request body — a key derived from the body cannot distinguish "the same request
retried" from "genuinely charging the customer twice for the same amount".

## Behaviour

When a request arrives with a key that has been seen before:

- If the original request **completed**, the original response is replayed with
  the same status code and body, plus the header `Idempotent-Replay: true`.
- If the original request is **still in flight**, the API returns `409
  Conflict` with error code `NW-4090`. Retry after a short delay.
- If the key was used with a **different request body**, the API returns `422
  Unprocessable Entity` with error code `NW-4220`. This is a bug in the
  integration, not a transient condition, and retrying will not help.

Idempotency keys are scoped per merchant and per endpoint. Two different
merchants can use the same key without colliding, and the same key on
`/v1/payments` and `/v1/refunds` refers to two separate operations.

## Retention

Keys are retained for **24 hours** from the time the original request
completed. After that the key is forgotten and a request carrying it is treated
as new. Any retry strategy that might still be running after 24 hours must
generate a fresh key and check the payment's status first, or it risks charging
the customer twice.

The 24-hour window is a deliberate trade. Longer retention means more storage
and a longer window in which a key collision can surprise someone; shorter
retention means a legitimate retry after a long outage is no longer protected.
24 hours covers every retry schedule we ship in our SDKs, with headroom.

## What is not covered

Idempotency protects against duplicate *requests*. It does not protect against:

- **Two different keys for the same intent.** If your retry logic generates a
  new key on each attempt, you have no idempotency at all. This is the single
  most common integration bug we see.
- **Duplicate customer actions.** A customer clicking "Pay" twice in two browser
  tabs produces two genuinely different operations, and we cannot tell that from
  two legitimate purchases.
- **Refund duplication across channels.** A refund issued through the dashboard
  and a refund issued through the API are separate operations with separate
  keys.

## Implementation notes

Keys live in Redis with a 24-hour TTL, keyed as
`idem:{merchant_id}:{endpoint}:{key}`. The stored value holds the request body
hash, the response status, the response body and a state flag.

The in-flight case is handled with `SET NX`: the first request to arrive claims
the key and writes state `in_flight`; a concurrent request sees the claim and
returns `NW-4090`. When the original request finishes, the entry is rewritten
with the response and state `complete`.

If Redis is unavailable, `payment-api` **rejects** write requests with `503`
rather than processing them without idempotency protection. This is one of very
few places where we fail closed instead of degrading: the cost of a duplicate
charge is far higher than the cost of a brief outage.
